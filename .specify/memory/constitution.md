# 软件测试总宪章

<!-- 本宪章为软件测试项目的最高级别约束文件，定义覆盖需求→设计→开发→测试→发布全生命周期的质量原则、实践标准与治理规则。 -->

## 核心原则

### 原则一｜质量八维模型（ISO/IEC 25010）

本项目的软件质量定义必须覆盖以下八个独立维度，每个维度必须定义可测量的子特性指标：

1. **功能适用性**（Functional Suitability）——功能完整覆盖声明需求、输出结果精确符合预期、功能设计匹配用户实际任务
2. **性能效率**（Performance Efficiency）——时间行为、资源利用率、容量
3. **兼容性**（Compatibility）——共存性、互操作性
4. **易用性**（Usability）——可学习性、可操作性、用户差错防护
5. **可靠性**（Reliability）——可用性、容错性、易恢复性
6. **安全性**（Security）——保密性、完整性、抗抵赖性、可核查性、真实性
7. **可维护性**（Maintainability）——模块化、可复用性、可分析性、可修改性、可测试性
8. **可移植性**（Portability）——适应性、可安装性、可替换性

**【示例】** 某华为云 ECS 实例规格变更功能的质量测试必须覆盖：规格变更逻辑正确性（功能适用性）、调度响应 <30s（性能效率）、多 Region 可用区互操作（兼容性）、控制台操作直观性（易用性）、调度失败自动重试（可靠性）、IAM 权限校验（安全性）、调度器接口可 Mock（可维护性）、跨 OS 镜像兼容（可移植性）。

### 原则二｜阶段衔接不可断裂

全生命周期必须遵循"需求→设计→开发→测试→发布"五阶段流水线，各阶段间存在刚性质量门禁，前一阶段未通过不得进入下一阶段：

| 阶段转换 | 前置门禁 | 转换条件 |
|---|---|---|
| 需求 → 设计 | 需求可测试性评审通过 | 需求条款 100% 可量化、可验证 |
| 设计 → 开发 | 威胁建模通过、架构可测试性评审通过 | 设计层无 P0/P1 风险 |
| 开发 → 测试 | 静态分析通过、单元测试覆盖率达标 | 无 Critical 告警、覆盖率 ≥ 85% |
| 测试 → 发布 | 准入准出标准全部满足、质量门禁通过 | 缺陷清零或风险已评估 |
| 发布后 | 生产监控上线、反馈回流闭环 | 异常告警与测试用例回流关联 |

**【示例】** 华为云 ECS 批次规格变更功能，需求阶段"变更后实例状态保持一致"条款缺乏量化定义，不得流转至设计阶段；修正为"变更后所有实例状态 5 分钟内同步"后方可通过门禁。

### 原则三｜可测试性为一级质量属性

系统的可测试性（Testability = 可控性 Controllability + 可观测性 Observability）必须在设计阶段即纳入约束，与功能、性能同等重要：

- 所有依赖必须提供可替换的测试替身（Test Double），遵循依赖注入设计
- 核心业务逻辑必须为纯函数或无副作用转换，确保相同输入始终输出相同结果
- 不可使用全局可变状态、硬编码时间、随机 UUID 等破坏测试确定性的设计
- 系统必须提供结构化日志，记录每次操作的前置状态、执行过程和后置结果
- 必须定义明确的接口边界（Seams），确保测试时可插入 Mock/Stub

**【示例】** Nova 计算服务的 FlavorValidator 模块设计：所有规格校验逻辑封装为纯函数 `validateFlavorChange(oldFlavor: FlavorSpec, newFlavor: FlavorSpec) -> ValidationResult`，入参明确、出参确定、无外部依赖，单元测试无需 Mock 任何组件即可执行。

## 阶段约束

### 第一章｜需求阶段

#### 1.1 需求可测试性评估

需求阶段的测试相关动作必须满足：

- 所有需求条款必须满足 **CCQV 标准**：无歧义（Consistent）、完整（Complete）、量化（Quantitative）、可验证（Verifiable）
- 不可量化或不可验证的需求不得通过需求评审
- 需求的优先级、影响范围、业务价值必须明确标注
- 需求必须与宪章"质量八维模型"中的对应维度建立映射关系
- 每条需求必须产出至少一条对应的测试场景（Test Scenario）

**【示例】** "规格变更后实例状态应保持一致"（不合格）→ 修正为"规格变更后所有实例状态在 5 分钟内同步"（合格）。

#### 1.2 需求阶段安全需求定义

- 必须识别功能涉及的资产类型、敏感程度、数据流向
- 必须定义用户角色与权限边界（RBAC/ABAC）
- 必须定义审计日志要求：记录内容、存储周期、防篡改要求
- 必须定义加密要求：传输加密、存储加密、密钥管理策略

#### 1.3 需求阶段输出交付物

| 交付物 | 责任方 | 验收标准 |
|---|---|---|
| 需求可测试性评估报告 | 测试工程师 | 每条需求均标注可测试性评级（A/B/C） |
| 安全需求清单 | 安全工程师 | 覆盖资产/权限/审计/加密四个维度 |
| 需求-测试场景映射表 | 测试工程师 | 1 条需求对应 ≥1 条测试场景 |
| 质量维度映射表 | 测试工程师 | 每条需求映射至八维模型对应维度 |

### 第二章｜设计阶段

#### 2.1 威胁建模（Threat Modeling）

- 必须使用 STRIDE 方法论（Spoofing/Tampering/Repudiation/Information Disclosure/DoS/Elevation of Privilege）
- 必须产出威胁建模报告，包含威胁清单、影响评估、缓解措施
- P0/P1 威胁必须在编码前消除或提供缓解方案
- 架构设计变更时必须重新执行威胁建模

#### 2.2 架构可测试性设计

- 必须定义模块/服务间的接口契约（Contract），包含输入/输出规格、错误码、超时约束
- 契约变更必须触发契约测试验证，确保不破坏消费者
- 必须确保所有外部依赖可在测试环境中替换为测试替身
- 必须提供本地可运行的测试环境，测试不得仅依赖 CI 环境

#### 2.3 流程定义

1. **业务主流程图**——使用 Mermaid 描述正常处理流程
2. **异常分支流程列表**——流程分支 ID、触发节点、触发条件、处理流程、优先级
3. **核心状态机定义**——使用 Mermaid 状态图描述关键对象状态迁移路径

#### 2.4 设计阶段输出交付物

| 交付物 | 责任方 | 验收标准 |
|---|---|---|
| 威胁建模报告 | 安全工程师 + 架构师 | STRIDE 全覆盖，P0/P1 威胁有缓解方案 |
| 架构可测试性评估报告 | 测试工程师 + 架构师 | 依赖可替换、日志结构化、接口契约明确 |
| 接口契约文档 | 架构师 + 开发者 | 契约可被契约测试工具解析和验证 |
| 流程 + 状态机 | 开发者 | Mermaid 语态可渲染，状态迁移完整 |

### 第三章｜开发阶段

#### 3.1 测试驱动开发循环（Red-Green-Refactor）

1. **Red（红）**：先编写一个失败的测试，该测试必须失败在预期位置
2. **Green（绿）**：仅编写足以让测试通过的最少生产代码，不优化、不处理未覆盖边界
3. **Refactor（重构）**：在全部测试通过的前提下改善代码结构，不改变外部行为
- 每次仅处理一个失败测试
- 测试执行反馈循环必须在秒级内完成
- 测试代码必须与生产代码同等对待——必须重构、去重、保持可读性

#### 3.2 测试金字塔与投入比例

| 测试层级 | 投入比例 | 执行速度 | 覆盖范围 | 技术要求 |
|---|---|---|---|---|
| 单元测试 | ≥70% | 秒级（<100ms/用例） | 核心业务逻辑路径 | 纯函数测试、Mock 依赖 |
| 集成测试 | ≥20% | 分钟级（<2min/用例） | 模块间交互、外部依赖 | 真实基础设施、契约测试 |
| E2E 测试 | ≤10% | 分钟级（<5min/用例） | 核心用户体验路径 | 自动化 UI/API 验证 |

#### 3.3 静态分析与代码质量门禁

- 必须在每次提交时执行静态分析，无 Critical/Blocker 告警方可进入下一阶段
- 代码规范检查必须 100% 通过，不允许使用 `@Suppress`、`// noinspection` 等方式绕过
- 代码复杂性指标必须达标（圈复杂度 ≤ 10，单方法行数 ≤ 50）

#### 3.4 开发阶段输出交付物

| 交付物 | 责任方 | 验收标准 |
|---|---|---|
| 单元测试 + 测试报告 | 开发者 | 覆盖率 ≥85%，执行通过率 ≥98% |
| 集成测试 + 测试报告 | 开发者 + 测试工程师 | 契约验证 100% 通过 |
| 静态分析报告 | CI 系统 | 无 Critical/Blocker 告警 |
| 代码复杂度报告 | CI 系统 | 圈复杂度、行数在阈值内 |

### 第四章｜测试阶段

#### 4.1 测试准入标准

- 需求文档已通过可测试性评审，所有需求条款满足 CCQV 标准
- 架构设计已完成威胁建模，P0/P1 威胁已消除或提供缓解方案
- 开发代码已完成静态分析且无严重告警
- 测试用例规格（Test Case Spec）已通过评审，每条用例有唯一标识、可追溯至需求
- 测试环境已就绪且可用，数据准备完成

#### 4.2 测试执行要求

- **全量覆盖**：定义的测试场景（正常/异常/边界）必须 100% 执行并记录结果
- **风险聚焦**：高风险模块占测试资源 40% 以上（帕累托 80/20 法则）
- **定期更新**：测试用例集必须定期审查和更新，防止"杀虫剂效应"
- **独立验证**：测试人员不得同时测试自己编写的代码

#### 4.3 测试事件与缺陷管理

- 每个测试异常必须产测试事件报告（Test Incident Report），包含预期结果、实际结果、严重程度
- 缺陷必须按严重度分级：P0（阻塞）/ P1（严重）/ P2（一般）/ P3（轻微）
- 缺陷修复必须在 SLA 内完成：P0 ≤ 24h、P1 ≤ 48h、P2 ≤ 1 个 Sprint
- 缺陷修复后必须执行回归验证，确认无连带影响

**【示例】** 测试执行 SC-03 时发现 Nova 调度器返回错误码与契约不符，必须产出事件报告：预期返回 409 Conflict，实际返回 500 Internal Server Error，严重度 P1，由 Nova 开发者 48h 内修复。

#### 4.4 测试准出标准

- 全部 P0/P1 测试用例 100% 通过
- 功能覆盖率 ≥定义目标值
- 代码覆盖率（业务路径）≥85%
- P0/P1 缺陷 100% 修复并验证
- P2 缺陷修复率 ≥90%，剩余缺陷已评估风险
- 测试总结报告已完成，包含质量评估和发布建议

#### 4.5 测试阶段输出交付物

| 交付物 | 责任方 | 验收标准 |
|---|---|---|
| 测试用例规格 | 测试工程师 | 用例可追溯至需求，每条用例有唯一标识 |
| 测试执行日志 | 测试工程师 | 每次执行记录完整结果，非"通过/失败"聚合 |
| 测试事件报告 | 测试工程师 | 预期/实际结果、严重程度、影响评估完整 |
| 测试总结报告 | 测试工程师 | 包含质量评估、发布建议、风险分析 |

### 第五章｜发布阶段

#### 5.1 质量门禁

| 门禁项 | 要求 | 验证方式 |
|---|---|---|
| 静态分析 | 无 Critical/Blocker 告警 | CI 系统自动验证 |
| 单元测试通过率 | ≥98% | CI 系统自动验证 |
| 代码覆盖率（业务路径） | ≥85% | 覆盖率工具自动验证 |
| 集成测试通过率 | 100%（P0/P1 用例） | CI 系统自动验证 |
| 安全扫描（SAST/DAST） | 无 P0/P1 漏洞 | 安全扫描工具自动验证 |
| 性能基准 | 核心接口响应时间 ≤ SLA 阈值 | 性能测试自动化验证 |
| 缺陷密度 | DI ≤ 定义阈值（按严重度加权） | 缺陷管理系统统计 |

#### 5.2 发布决策规则

- 质量门禁未通过 → 不得发布
- P0/P1 缺陷未清零 → 不得发布
- 测试总结报告缺失 → 不得发布
- 若存在 P2 缺陷但风险可接受，经项目负责人审批后方可发布
- 所有发布决策必须记录决策人、时间和依据

#### 5.3 发布后回流

- 功能发布后必须立即上线生产监控告警
- 生产异常告警必须回传至测试系统，与相关测试用例建立关联
- 生产中发现的缺陷必须作为回归测试用例加入下一轮测试循环
- 每个版本必须在发布后 7 个自然日内完成发布回顾

#### 5.4 发布阶段输出交付物

| 交付物 | 责任方 | 验收标准 |
|---|---|---|
| 质量门告警 | CI 系统 + 测试负责人 | 全部门禁项状态为"通过"或"豁免+审批" |
| 发布决策记录 | 项目负责人 | 决策人、时间、依据完整可追溯 |
| 发布回顾报告 | 测试工程师 | 总结质量数据、改进项、遗留风险 |

## 治理规则

### 阶段流转控制图

```
需求阶段 → [CCQV 评审通过] → 设计阶段 → [威胁建模通过] → 开发阶段
  ↑                                              ↓
  ← [需求变更回流]                              [静态分析+覆盖率达标] → 测试阶段
  ↑                                              ↓
  ← [测试事件驱动回归]                            [准入准出全部满足] → 发布阶段
  ↑                                              ↓
  ← [生产缺陷回流]                              [生产监控上线]
```

### 宪章修正流程

1. **提议**：任何团队成员可发起修正提议，必须提供充分理由
2. **评审**：测试治理组织必须在 5 个工作日内完成评审
3. **审批**：项目负责人审批通过后方可生效
4. **版本**：采用语义化版本控制——移除原则为 MAJOR，新增为 MINOR，修正为 PATCH
5. **传播**：宪章变更必须同步更新所有依赖模板（测试模板、计划模板、任务模板）

### 失败测试处理规则

- 测试失败必须立即归类：代码缺陷 / 测试缺陷 / 环境问题
- 代码缺陷：开发者在 SLA 内修复（P0: 24h, P1: 48h, P2: 1 Sprint）
- 测试缺陷：测试工程师修正测试用例并更新
- 间歇性故障（Flaky Test）必须记录 1 个 Sprint 内修复或禁用
- **禁止以 `@Skip`、`@Ignore` 等方式沉默失败而不在 SLA 内解决**

### 宪章效力

- 本宪章为最高级别约束文件，高于所有项目内其他实践、规范和指南
- 当其他规范与宪章冲突时，以宪章为准
- 任何变通必须走修正流程，不得自行绕过
